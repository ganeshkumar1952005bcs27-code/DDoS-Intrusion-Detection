# DDoS Mitigation in SD-IoT — Full Implementation

Implements the full pipeline based on Ali, Song, Sharma & Al-Khasawneh,
*"DDoS Intrusions Detection in Low Power SD-IoT Devices Leveraging
Effective Machine Learning,"* IEEE Trans. Consumer Electronics, Vol. 71,
No. 1, Feb 2025:

```
IoTID20 → Preprocessing → HANP (AHP+ANP) ranks DT best for TinyML
                        → PCA reduces features (Algorithm 2)
                        → Decision Tree trained on PCA components
                        → Edge node classifies traffic (HARDWARE ESP32
                          or SOFTWARE simulator — you choose)
                        → Intrusion Alert → Communication Layer (HTTP)
                        → Ryu SDN Controller → Threat Validation
                        → Mitigation Engine → OpenFlow Rule
                        → OpenFlow Switch → BLOCK / ALLOW
```

---

## 0. Hardware vs. Software — which do I use?

**You can run this project either way, and both talk to the exact same
controller without any changes on the controller side.**

| | Hardware mode | Software mode |
|---|---|---|
| What runs the model | A real ESP32 board, running `esp32/esp32_tinyml_ids.ino` | Your PC, running `scripts/simulate_edge_node.py` |
| What the model is | `esp32/generated_model.h` — the scaler+PCA+tree compiled to plain C | `outputs/scaler.joblib`, `outputs/pca.joblib`, `outputs/decision_tree.joblib` — the **same** fitted model, loaded with scikit-learn |
| Traffic source | Real flow features you extract on-device (you wire this in — see the `.ino`'s `getRawFeatureVector()`) | Replayed rows from the training dataset, or piped in over stdin |
| Requires | An ESP32 board, Arduino IDE, WiFi | Nothing extra — just Python |

Set your choice in `config.json` under `"edge_node": {"mode": "hardware"
| "software"}` — this is documentation for you/your team; it doesn't
change any code path automatically, it's just so everyone knows which
one is active. **You can also run both at once** (e.g. a real ESP32 in
one room + the software simulator for load-testing) since they're
independent processes hitting the same REST endpoint.

Skip to **§3B** for hardware, **§3C** for software.

**Which machine runs what:**

| Component | Where | Why |
|---|---|---|
| `ml/`, `scripts/run_all.py` | Your PC/laptop | One-time/occasional training step. |
| `esp32/` | A real ESP32 board (hardware mode only) | This *is* the low-power edge device. |

## 2. Setup

```bash
# 1. Copy and edit the config file
cp config.example.json config.json
# edit config.json: wifi_ssid/password (hardware mode), controller.alert_url,
# dataset.csv_path, thresholds, etc.

# 2. Install ML-side dependencies (on your PC)
pip install -r requirements.txt

# 3. (Optional) Get the real dataset
# Download IoTID20 from:
#   https://sites.google.com/view/iot-network-intrusion-dataset/home
# Save it at the path set in config.json -> dataset.csv_path
# (default: data/IoTID20.csv). If you skip this, ml/dataset.py
# auto-generates a structurally realistic synthetic stand-in so the
# pipeline still runs end-to-end.

# 4. Install controller-side dependencies (on the Linux SDN host)
cd controller && pip install -r requirements.txt && cd ..
# If Ryu fails to build (common with modern setuptools):
#   pip install "setuptools<58" ryu eventlet==0.30.2 webob
```

## 3A. Step 1 — Train everything (always required, both modes)

```bash
python3 scripts/run_all.py
```

Runs, in order, and prints progress for each:
1. **HANP** (`ml/hanp.py`) — AHP criteria weights + consistency ratio,
   ANP local priorities per criterion, final ranking. Saves
   `outputs/hanp_ranking.csv`. Reproduces the paper's DT > RF > SVM > KNN.
2. **Dataset load** (`ml/dataset.py`) — real CSV or synthetic fallback.
3. **PCA analysis** (`ml/pca_reduction.py`, Algorithm 2) — finds `Fm`,
   saves `outputs/pca_variance.csv`.
4. **Benchmark** (`ml/train_evaluate.py`) — trains/evaluates DT/RF/SVM/
   KNN on original vs. PCA-reduced features, saves
   `outputs/ml_performance_results.csv`.
5. **Final export** (`ml/train_export.py`) — trains the deployed
   pipeline **raw → StandardScaler → PCA(Fm) → DecisionTree** (the
   HANP-selected model, trained on PCA components as in the paper), and
   writes:
   - `outputs/scaler.joblib`, `outputs/pca.joblib`, `outputs/decision_tree.joblib`
     (used by the **software** edge simulator)
   - `outputs/model_metadata.json` (feature order + metrics, read by
     both deployment paths so they agree on input format)
   - `esp32/generated_model.h` (the **same** scaler+PCA+tree, compiled
     to plain C, used by the **hardware** ESP32 sketch)

You can also run any single stage on its own from the project root:
```bash
python3 -m ml.hanp
python3 -m ml.dataset
python3 -m ml.pca_reduction
python3 -m ml.train_evaluate
python3 -m ml.train_export
```

## 3B. HARDWARE path — flash a real ESP32

1. Install Arduino IDE 2.x → Boards Manager → "esp32 by Espressif Systems".
2. Open `esp32/esp32_tinyml_ids.ino` (the folder is the sketch;
   `generated_model.h` appears as a second tab automatically).
3. Edit these to match `config.json`:
   ```cpp
   const char* WIFI_SSID     = "YOUR_WIFI_SSID";
   const char* WIFI_PASSWORD = "YOUR_WIFI_PASSWORD";
   const char* CONTROLLER_URL = "http://<controller-ip>:8080/api/alert";
   ```
   (The ESP32 can't read the JSON config file directly, so these three
   lines must be copied in by hand.)
4. **Tools → Board → ESP32 Dev Module**, pick the COM port, **Upload**.
5. Open Serial Monitor at **115200 baud**. You'll see the expected raw
   feature count and PCA component count printed, then `WiFi connected`.
6. For bench-testing without real network traffic, type a
   comma-separated line of `NUM_RAW_FEATURES` values into the Serial
   Monitor and press Enter — the sketch classifies it (running the full
   scaler→PCA→tree pipeline on-device) and, if flagged as an attack,
   POSTs an alert to the controller.
7. For production use, replace `getRawFeatureVector()` and
   `getSuspectedSrcIP()` in the `.ino` with your real flow-metering code
   — see the comments at those functions for exactly what's needed.

## 3C. SOFTWARE path — no ESP32 required

```bash
python3 scripts/simulate_edge_node.py --mode replay --limit 100 --delay 1.0
```
Loads the identical `scaler.joblib` + `pca.joblib` + `decision_tree.joblib`
pipeline, replays real rows from the training dataset (or synthetic
stand-in), classifies each one, and POSTs alerts to
`config.json -> controller.alert_url` exactly like the ESP32 would.

Alternative: feed your own feature rows over stdin:
```bash
echo "1.2,3.4,...,80 comma-separated values..." | \
    python3 scripts/simulate_edge_node.py --mode stdin
```

## 4. Start the SDN controller

```bash
ryu-manager controller/ryu_mitigation.py
```
Runs from the project root so it can find `config.json`. Starts:
- An OpenFlow 1.3 L2 learning switch handler (normal traffic still forwards).
- REST API on `config.json -> controller.host:port` (default `0.0.0.0:8080`):
  - `POST /api/alert` — the Communication Layer endpoint both edge modes hit.
  - `GET /api/status` — connected switches + currently blocked IPs.
- **Threat validation**: cross-checks the edge model's verdict against
  the controller's own observed OpenFlow packet-in rate for that
  source (tunable via `config.json -> controller.packetin_rate_threshold`).
- **Mitigation engine**: installs a high-priority OpenFlow drop rule for
  the offending source IP, auto-expiring after
  `controller.block_idle_timeout_seconds` (default 60s).
- Logs every decision + timing to `controller/controller_events.log`.

## 5. (Optional) Test with Mininet

```bash
sudo python3 network/mininet_topology.py
```
Needs a real Linux host/VM with Mininet + Open vSwitch (cannot run
inside a typical sandbox — needs root + raw sockets). Brings up hosts
from `config.json -> network` behind one OpenFlow switch pointed at the
controller. See the script's docstring for a `curl` example that
simulates an alert directly, without needing real attack traffic to
trip the rate heuristic.

## 6. Design notes

- **Hardware and software modes use the exact same model.** `generated_model.h`
  and the three `.joblib` files are produced from the *same* fitted
  `train_pipeline()` call in `ml/train_export.py` — one is a C
  translation, the other is the native scikit-learn objects. Given
  identical raw feature input, both produce identical predictions.
- **Why PCA on-device, not just raw-feature selection:** the scaler+PCA
  transform is a modest matrix-vector multiply (O×Fm floats, e.g.
  80×32 ≈ 10 KB), trivial for an ESP32 (240 MHz, 320 KB RAM). This lets
  the deployed model match what the paper actually evaluates — a
  Decision Tree trained on PCA-reduced components — instead of quietly
  substituting a different (raw-feature) model at deploy time.
- **Threat validation is defense-in-depth by design**: the controller
  never blindly trusts a single edge sensor — see `_validate()` in
  `controller/ryu_mitigation.py`.
- **Blocks self-expire** so a false positive doesn't permanently cut off
  a legitimate device.

## 7. Known limitations

- The synthetic dataset (used when `data/IoTID20.csv` is absent) is a
  structural stand-in only; swap in the real CSV for results comparable
  to the paper's reported 99%+ metrics.
- `ryu` is an older package; it may need Python 3.8/3.9 or
  `setuptools<58` to install cleanly.
- Mininet requires root/raw sockets and cannot run inside this sandbox
  — run `network/mininet_topology.py` on your own Linux machine/VM.
- `esp32_tinyml_ids.ino`'s `getRawFeatureVector()` / `getSuspectedSrcIP()`
  are reference placeholders (Serial-injection for bench testing); wire
  them to your real packet/flow-metering source for production use.
